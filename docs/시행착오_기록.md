# 시행착오 기록

이 실습 과정에서 실제로 부딪힌 문제와 해결 과정을 정리한다. 결과물(`docs/log.md`, `docs/index.html`)에는 "무엇을 확인했는지"가 정리돼 있다면, 이 문서에는 "왜 막혔고 어떻게 뚫었는지"를 남긴다.

## 1. GitHub push 인증: HTTPS 비밀번호 실패 → SSH Deploy Key

- `git push` 시 GitHub 계정 비밀번호를 입력했더니 `remote: Invalid username or token. Password authentication is not supported for Git operations.` — GitHub가 2021년부터 HTTPS 비밀번호 인증을 폐지한 걸 몰랐음.
- 해결: `ssh-keygen`으로 전용 키(`~/.ssh/id_ed25519_github`) 생성 → 이 repo에 Deploy Key(Read/write)로 등록 → `~/.ssh/config`에 `Host github.com` 항목 추가 → `git remote set-url origin git@github.com:...`로 전환.

## 2. git 커밋 author 이메일 오설정

- `git config --global user.email`을 회사 이메일로 잘못 설정했다가, 실제 GitHub 계정용 이메일로 정정.
- 여러 머신에서 같은 계정으로 커밋할 땐 이메일을 통일해야 커밋 히스토리에서 동일 인물로 잡힌다.

## 3. 벤더 커널이라 perf가 설치되지 않음

- `perf --version` → `WARNING: perf not found for kernel 6.8.12-1021`. Jetson의 L4T 커널은 NVIDIA가 커스텀 빌드한 버전이라, Ubuntu 표준 저장소에 `linux-tools-6.8.12-1021-tegra` 패키지가 존재하지 않음.
- 해결: 버전이 다른 표준 `linux-tools-generic`(`6.8.0-138-generic`) 패키지에 포함된 `perf` 바이너리를 커널 버전 체크 없이 절대경로로 직접 실행. perf의 이벤트 파싱 로직이 커널 ABI에 크게 의존하지 않아 정상 동작.
- 부작용: `sudo perf ...`라고 치면 시스템 기본 wrapper(`/usr/bin/perf`)를 찾아가서 다시 실패함 — `sudo`는 alias를 무시하기 때문. `PERF=/usr/lib/linux-tools/6.8.0-138-generic/perf`처럼 변수에 절대경로를 담아 `sudo $PERF ...`로 호출해야 함.

## 4. fib(35)가 너무 빨리 끝나서 샘플링 부족

- 처음 `fib(35)`는 0.099초 만에 끝나서 `perf record` 샘플이 부족할 뻔함. `fib(42)`로 올려서 2.5초짜리 부하로 조정.

## 5. clang-format이 짧은 함수를 한 줄로 유지함

- 기본 LLVM 스타일은 `AllowShortFunctionsOnASingleLine`이 허용이라 `fib` 함수가 한 줄로 남고 `main`만 여러 줄로 포맷됨.
- `.clang-format`에 `AllowShortFunctionsOnASingleLine: None`을 명시해서 모든 함수가 동일하게 멀티라인으로 펼쳐지도록 함.

## 6. ftrace의 function/function_graph tracer가 아예 없음

- `available_tracers`를 확인하니 `nop`밖에 없었음 — 이 Tegra 커널은 `CONFIG_FUNCTION_TRACER`/`CONFIG_FUNCTION_GRAPH_TRACER` 자체를 빼고 빌드됨.
- 대안: `available_events`(1,877개)에 남아있는 정적 tracepoint(`raw_syscalls:sys_enter/exit`, `sched:sched_switch`, `sched:sched_migrate_task`)로 실습 방향을 바꿈.

## 7. `perf stat`의 `:u` 접미사 때문에 커널 활동이 안 보임

- `sudo` 없이 `perf stat`을 돌리면 이벤트 이름에 `:u`가 붙고, user-space에서 발생한 것만 카운트함.
- I/O 바운드 프로그램(`io_bound`)은 시간의 93%가 커널 안(`write()` syscall 처리)에서 벌어지는데, `:u` 카운터로는 그 부분이 통째로 안 보여서 `cycles`가 비정상적으로 작게 나왔음.
- 해결: `sudo`로 실행해 커널 모드 사이클까지 포함해서 재측정.

## 8. 같은 벤치마크를 두 번 돌렸더니 결과가 확 달라짐

- `io_bound`를 `time`으로 처음 쟀을 땐 `real 2.058s`, `sudo perf stat`으로 다시 쟀을 땐 `0.686s`.
- 같은 파일(`/tmp/io_bound_test.bin`)에 대해 두 번째 실행이라 파일시스템 블록 할당/페이지 캐시가 이미 준비된 상태였을 가능성이 높음.
- 교훈: 벤치마크는 한 번 측정으로 끝내지 말고 여러 번 반복해서 확인해야 신뢰할 수 있다.

## 9. ftrace 트레이스 버퍼가 고빈도 이벤트로 오버플로

- `io_bound`가 `write()`를 200만 번 호출했는데, 트레이스에는 14,727번만 잡힘.
- ftrace의 기본 버퍼는 circular(순환) 방식이라, 이벤트가 너무 자주 발생하면 오래된 기록을 새 기록이 덮어씀 — 결국 프로그램이 끝나기 직전 ~22ms 구간만 남음.
- 고빈도 이벤트를 온전히 잡으려면 `buffer_size_kb`를 미리 키워야 한다는 걸 확인.

## 10. pid 필터링 없이 트레이싱하면 노이즈에 신호가 묻힘

- `multithread` 실행 중 `sched_migrate_task`를 무필터로 잡았더니 105줄 중 대부분이 `rcu_preempt`, `kworker`, `sshd`, `python`, `containerd` 등 우리 프로세스와 무관한 시스템 배경 활동이었음.
- 진짜 우리 스레드의 마이그레이션(3건)을 찾으려면 `grep 'comm=<우리 프로세스명>'`처럼 필터링이 필요했음. 실전에서는 `set_event_pid`로 아예 커널 레벨에서 필터링하는 게 정석.

## 11. 컴파일된 바이너리를 실수로 여러 번 커밋

- `src/hot`, `src/io_bound`, `src/multithread` 실행 파일이 `.c` 소스와 함께 매번 `git add -A`에 딸려 들어가 커밋됨.
- `.gitignore`에 바이너리 이름을 추가하고 `git rm --cached`로 정리. 처음부터 `.gitignore`를 준비해뒀으면 반복 작업을 줄일 수 있었음.
