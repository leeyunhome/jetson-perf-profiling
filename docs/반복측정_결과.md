# 반복 측정 결과 (5회)

## 이 문서의 목적

[`시행착오_기록.md`](시행착오_기록.md) 8번에 "같은 벤치마크를 두 번 돌렸더니 결과가 확 달라졌다 → 벤치마크는 여러 번 재야 한다"고 적어뒀지만, 그건 **교훈을 메모한 것이지 결과로 확인한 것이 아니었다.** 이 문서가 그 문제의식을 실제 데이터로 매듭짓는다.

측정 스크립트: [`scripts/bench.sh`](../scripts/bench.sh) (`bash scripts/bench.sh 5`)

결론부터 요약하면 **반복 측정이 기존 문서의 결론 두 개를 반증했다.** 아래 "발견 2, 3"이 그것이다.

## 측정 조건

| 항목 | 값 |
|---|---|
| Kernel | `6.8.12-1021-tegra` |
| Cores | 6 |
| perf | `/usr/lib/linux-tools/6.8.0-138-generic/perf` (6.8.12) |
| CPU governor | `schedutil` |
| Power mode | **15W** (`nvpmodel -q`) |
| `/tmp` 파일시스템 | **ext4** (tmpfs가 아님 → I/O 워크로드는 실제 디스크 writeback 발생) |
| `fs.protected_regular` | **2** (발견 2의 직접 원인) |

## 측정 방법 (2-pass)

동일 워크로드를 서로 독립적인 두 방법으로 재서 교차 검증했다.

1. **Pass 1** — 일반 유저 권한으로 5회 실행, **매 회의 개별 wall-clock을 그대로 기록**. 평균만 내면 첫 실행 이상치가 묻히기 때문에 개별값을 남긴다.
2. **Pass 2** — `sudo perf stat -r 5`. perf가 5회를 직접 반복하며 이벤트별 평균 ± 상대표준편차를 계산한다. 커널 모드까지 집계하려면 `sudo`가 필수다.

## 결과 1 — wall clock (Pass 1, 단위 ms)

| 워크로드 | 1 | 2 | 3 | 4 | 5 | 평균 | 표준편차 | range | 상대편차 |
|---|---|---|---|---|---|---|---|---|---|
| `hot` | 2566 | 2584 | 2590 | 2565 | 2585 | **2578.0** | 11.6 | 2565–2590 | 0.5% |
| `io_bound` | 2021 | 2071 | 2077 | 2040 | 2057 | **2053.2** | 23.0 | 2021–2077 | 1.1% |
| `multithread` | 391 | 389 | 390 | 391 | 392 | **390.6** | 1.1 | 389–392 | 0.3% |

**첫 실행이 느리다는 패턴은 없다.** `hot`은 1회차가 오히려 최솟값이고, `io_bound`도 1회차(2021ms)가 최솟값이다. 캐시 워밍업으로 첫 실행이 느려지는 현상은 관측되지 않았다.

## 발견 1 — 어떤 지표는 1회만 재도 되고, 어떤 지표는 절대 안 된다

같은 5회 측정 안에서 지표별 상대표준편차가 **0.00%부터 60%까지** 벌어진다.

| 지표 | 상대편차 범위 | 성격 |
|---|---|---|
| instructions, branches | **±0.00 ~ 0.29%** | 결정론적 — 실행할 명령어 수는 코드가 정한다 |
| cycles, task-clock, elapsed | ±0.02 ~ 0.84% | 거의 결정론적 (주파수/캐시 상태에 약간 흔들림) |
| page-faults | ±0 ~ 0.39% | 안정 |
| branch-misses | ±1.79 ~ 3.97% | 보통 |
| **context-switches** | **±10.57 ~ 36.69%** | 불안정 — 그 순간 시스템에 뭐가 돌고 있었나에 의존 |
| **cpu-migrations** | **±36.74 ~ 60.00%** | 매우 불안정 — 1~2건 수준이라 1건 차이가 곧 50% |

실무적으로 중요한 결론: **IPC나 instruction 수는 1회 측정값을 인용해도 무방하지만, context-switch·migration 횟수는 1회 측정값을 근거로 어떤 주장도 할 수 없다.** 이 저장소의 초기 문서가 정확히 그 실수를 했고, 아래 발견 3이 그 사례다.

## 발견 2 — `io_bound` 0.686s는 캐시 효과가 아니라 **무효한 측정**이었다 (기존 결론 반증)

기존 문서(`시행착오_기록.md` 8번, `log.md` 8절)는 이렇게 적고 있었다:

> `io_bound`를 `time`으로 처음 쟀을 땐 `real 2.058s`, `sudo perf stat`으로 다시 쟀을 땐 `0.686s`. → 캐시 워밍업 효과로 추정.

**재현되지 않는다.** 동일 조건(`sudo`)에서 5회 반복한 결과는 **2.0615 ± 0.0149s (±0.72%)** 로, 0.686s와는 3배 차이가 나며 근처에도 오지 않는다.

진짜 원인은 캐시가 아니라 **에러 체크 누락으로 인한 무효 측정**이었다. 근거는 카운터 산술이다.

| | 문제의 런 (0.686s) | 정상 런 (2.06s) | 해석 |
|---|---|---|---|
| instructions | 1,353,862,063 | 5,911,112,075 | |
| **instr / 루프 1회** | **677** | **2,956** | 4.4배 적음 = 일을 안 했다 |
| **ns / 루프 1회** | **343 ns** | **1,028 ns** | 실패 syscall 왕복 시간 |
| IPC | 1.34 | 1.91 | |
| page-faults | 43 | 53 | 128MB를 실제로 안 씀 |
| context-switches | 7 | 42 | writeback 대기가 없었음 |

당시 `io_bound.c`에는 `open()` 반환값 검사가 없었다. `/tmp`가 sticky·world-writable이고 `fs.protected_regular=2`이므로, 앞선 유저 권한 실행이 남긴 `manager` 소유 파일을 root가 `O_CREAT`로 열면 **EACCES로 거부된다.** 그런데 코드가 이를 검사하지 않아 `fd = -1`을 들고 루프에 진입했고, 결국 **`write(-1, ...)`를 200만 번 호출하며 전부 EBADF로 즉시 실패하는 시간**을 측정했다. 루프당 677 instruction / 343ns는 "실패하는 syscall 왕복"의 비용으로 정확히 들어맞는다.

이번 세션에서도 동일 버그가 재현됐다 — 수정 전 `sudo perf stat -r 5`는 5회 전부 `open: Permission denied`를 뱉으며 task-clock **0.50ms**를 기록했다. (이때는 `perror` 덕분에 즉시 눈에 보였다.)

**이 사례의 교훈이 이 저장소에서 가장 값어치 있는 부분이다.** 반환값 검사 누락은 크래시 위험에 그치지 않고, **그럴듯해 보이지만 아무 의미 없는 벤치마크 수치를 만들어냈고, 그 수치가 "캐시 워밍업"이라는 잘못된 인사이트로 문서에 기록됐다.** 반환값 검사와 반복 측정 중 **하나만 있었어도** 잡혔을 오류다.

수정 내역: 출력 경로를 uid별로 분리(`/tmp/io_bound_test.<uid>.bin`, `IO_BOUND_OUT`로 override 가능)하고 생성 전 `unlink`하도록 변경. `open`/`write`/`close` 전부 반환값 검사 추가.

## 발견 3 — "멀티스레드에서 처음으로 context-switch가 0이 아니게 나왔다"도 사실이 아니었다 (기존 결론 반증)

기존 문서(`log.md` 9절, `index.html` 7절)는 멀티스레드 워크로드를 두고 "이번 실습 전체에서 **처음으로** `context-switches`/`cpu-migrations`가 0이 아니게 나왔다"고 적었다.

**측정 scope를 섞어서 비교한 결과였다.** 초기 세션에서 단일 스레드 워크로드는 `sudo` **없이** 측정해 `:u`(user-mode only) 스코프였고, 멀티스레드만 `sudo`로 측정했다. 커널이 개입하는 컨텍스트 스위치는 `:u` 스코프에 애초에 집계되지 않으므로, 0이 나온 건 워크로드 특성이 아니라 **측정 방식의 산물**이었다.

세 워크로드를 모두 `sudo`로 통일해 재측정한 결과:

| | context-switches | cpu-migrations |
|---|---|---|
| `hot` (단일 스레드) | **22** (±36.69%) | **2** (±36.74%) |
| `io_bound` (단일 스레드) | **42** (±16.45%) | **2** (±60.00%) |
| `multithread` (4 스레드) | 49 (±10.57%) | 1 (±48.99%) |

**단일 스레드 워크로드도 컨텍스트 스위치와 코어 마이그레이션을 겪는다.** 게다가 `cpu-migrations`는 `multithread`가 오히려 더 적게 나왔다(1 vs 2) — 상대편차가 37~60%인 지표라 이 차이 자체는 무의미하다.

멀티스레드 워크로드의 실제 구별점은 컨텍스트 스위치의 유무가 아니라 **`CPUs utilized 3.905`** 다. 이건 상대편차 0.47%로 안정적이며, 병렬 실행을 명확히 입증하는 유일한 지표다.

## 종합 교훈

1. **측정 조건을 워크로드 간에 통일하지 않으면 비교 자체가 무의미하다.** `sudo` 유무 하나로 결론이 뒤집혔다 (발견 3).
2. **에러 체크 없는 벤치마크는 조용히 거짓말을 한다.** 크래시는 눈에 보이지만, 무효한 측정값은 그럴듯한 인사이트로 위장한다 (발견 2).
3. **지표마다 필요한 반복 횟수가 다르다.** instruction 수는 1회로 충분하고, migration 횟수는 5회로도 부족하다 (발견 1).
4. 1~3은 모두 "한 번 재고 결론 내리기"에서 비롯됐다. 반복 측정은 정밀도를 높이는 작업이 아니라, **틀린 결론을 걸러내는 장치**였다.
