Jetson Orin에서 perf로 실물 ARM 하드웨어 프로파일링하기

ARM Cortex-A78AE (Jetson Orin) L4T 6.8.12-1021-tegra perf Flame Graph

배경

VirtualBox 가상머신에서는 perf stat을 실행해도 소프트웨어 이벤트(task-clock, page-faults)만 수집되고 하드웨어 PMU 이벤트(cycles, instructions, branches)는 <not supported>로 나온다. 가상화 계층이 게스트에 PMU를 노출하지 않기 때문이다. 이 제약을 확인하기 위해 실물 ARM 하드웨어인 Jetson Orin에서 동일한 실험을 재현했다.

1. 벤더 커널에서 perf 설치하기

Jetson의 커널은 NVIDIA가 커스텀 빌드한 6.8.12-1021-tegra라, Ubuntu 표준 저장소에는 이 정확한 버전에 대응하는 linux-tools-6.8.12-1021-tegra 패키지가 존재하지 않는다. 

$ perf --version
WARNING: perf not found for kernel 6.8.12-1021
  You may need to install the following packages for this specific kernel:
    linux-tools-6.8.12-1021-tegra
    linux-cloud-tools-6.8.12-1021-tegra

우회책: Ubuntu 표준 linux-tools-generic 계열(6.8.0-138-generic)에 포함된 perf 바이너리를 커널 버전 체크 wrapper 없이 직접 실행. perf의 이벤트 파싱 로직은 커널 ABI에 크게 의존하지 않아 정상 동작을 확인했다. 

PERF=/usr/lib/linux-tools/6.8.0-138-generic/perf
$PERF stat -- ls /

VM에서는 못 봤던 cycles, instructions, branches, branch-misses가 전부 정상 수집됐다. 실물 하드웨어의 이점을 직접 확인한 부분.

3. CPU 부하 예제 + Flame Graph

재귀 fib(42)를 -O0으로 컴파일(인라이닝 방지)해 약 2.5초짜리 CPU 부하를 만들고, perf record -g로 콜스택을 샘플링(10,358 샘플)한 뒤 Brendan Gregg의 FlameGraph 툴체인으로 시각화했다.

fib(n-1)+fib(n-2) 재귀 구조가 위로 갈수록 폭이 좁아지는 "뾰족탑" 모양으로 그대로 드러난다 (왼쪽 가지가 더 깊이 파고들고 오른쪽 가지는 상대적으로 얕게 끝남). 폭 100%가 거의 전부 fib에 집중돼 있어 핫스팟이 명확한 교과서적 사례.

fib처럼 분기 패턴이 규칙적인 연산 집중형 루프는 분기 예측기가 거의 완벽하게 학습되어 미스율이 0.01% 수준까지 떨어지고, IPC도 3.37까지 올라간다 (ARM 슈퍼스칼라 파이프라인이 거의 스톨 없이 가동). 반면 ls는 초단명 프로세스라 동적 링킹·파일시스템 조회의 불규칙한 분기와 예측기 워밍업 부족으로 미스율이 500배 가까이 높고 IPC도 1 미만이다.

5. ftrace: 벤더 커널 제약과 perf/ftrace scope 차이

available_tracers를 확인하니 nop만 존재했다 — Tegra 커스텀 커널이 function/function_graph tracer를 컴파일에서 아예 제외한 것이다. 대신 정적 tracepoint 기반 이벤트(1,877개 중 raw_syscalls:sys_enter/exit, sched:sched_switch)는 살아있어 이걸로 실습을 이어갔다. 

$ sudo cat /sys/kernel/debug/tracing/available_tracers
nop

fib(42) 실행 중 syscall은 시작 직후 0.42ms 구간(런타임 초기화: mprotect, munmap, rt_sigaction 등)에만 몰려있고, 이후 2.5초의 연산 구간은 완전히 조용했다 — 순수 유저모드 CPU 바운드 워크로드임을 커널 레벨에서 재확인.

예상 밖의 발견: perf stat과 ftrace가 다른 그림을 보여준 이유

perf stat에서는 context-switches:u 0이었는데, ftrace 로그에는 hot 프로세스가 irq/189-aerdrv, kworker/0:2로 여러 차례 sched_switch되는 게 찍혀 있었다. 모순이 아니라, perf stat 결과의 :u 접미사가 user-space 이벤트만 카운트한다는 뜻이라, 커널 인터럽트(PCIe AER)에 의한 선점은 애초에 집계 대상이 아니었던 것이다. ftrace는 커널 레벨을 전부 잡아내므로 이 선점이 그대로 드러났다.

교훈: 도구마다 "무엇을 세는지(scope)"가 다르면 겉보기 모순처럼 보이는 결과가 나올 수 있다. perf와 ftrace를 같이 써야 이런 걸 정확히 해석할 수 있다는 걸 직접 경험한 사례.

6. 세 번째 워크로드: I/O 바운드와 최종 비교

write()를 200만 번 반복하는 io_bound.c를 추가로 만들어 비교했다. time 결과는 user 0.148s / sys 1.907s로 fib(전부 user)와 정반대였다. 흥미롭게도 같은 파일에 대해 sudo perf stat으로 재측정하니 실행시간이 0.686초로 단축됐는데, 캐시 워밍업 효과로 추정된다 — 벤치마크는 한 번이 아니라 여러 번 재서 검증해야 한다는 실전 교훈이었다.

ftrace로는 또 다른 문제를 발견했다: write(syscall NR 64)가 200만 번 호출됐지만 트레이스에는 14,727번만 잡혔다. 기본 circular 버퍼가 고빈도 이벤트로 꽉 차서 마지막 ~22ms만 남기고 앞부분이 다 덮어써진 것이다. 이벤트가 적었던 fib(135줄)는 전체가 다 잡혔던 것과 대조적 — 고빈도 트레이싱에는 buffer_size_kb 조정이 필요하다는 것도 실습으로 확인했다.
