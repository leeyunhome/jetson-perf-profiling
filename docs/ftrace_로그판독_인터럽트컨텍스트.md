# ftrace 로그의 플래그 열 판독 — 이미 캡처한 로그에서 인터럽트 컨텍스트 찾기

## 이 문서의 출발점

앞선 실습([`log.md`](log.md) 7·9절)에서 ftrace 로그를 대량으로 캡처했지만, **매 줄 앞에 붙는 5글자 플래그 열을 읽지 않고 지나쳤다.** 이 문서는 새로 측정하지 않고, **이미 캡처해둔 로그를 다시 읽는 것**만으로 인터럽트 컨텍스트·선점 상태·스케줄러 동작을 규명한다.

결과적으로 **캡처는 해놓고 해석하지 못했던 현상 세 가지**를 설명할 수 있게 됐다.

## 플래그 열은 자기 설명적이다

ftrace 출력 헤더에 의미가 이미 적혀 있다 (Raspberry Pi, 커널 6.12.25 기준 — Jetson도 동일 포맷):

```
#                                _-----=> irqs-off/BH-disabled
#                               / _----=> need-resched
#                              | / _---=> hardirq/softirq
#                              || / _--=> preempt-depth
#                              ||| / _-=> migrate-disable
#                              |||| /     delay
#           TASK-PID     CPU#  |||||  TIMESTAMP  FUNCTION
```

즉 5글자는 각각 아래를 뜻한다.

| 자리 | 의미 | 값 |
|---|---|---|
| 1 | irqs-off / BH-disabled | `d` = 인터럽트 비활성, `.` = 활성 |
| 2 | need-resched | `N`/`n`/`p` = 재스케줄 요청 걸림, `.` = 없음 |
| 3 | **hardirq / softirq** | `h` = hardirq, `s` = softirq, `H` = softirq 안에서 hardirq, `.` = 프로세스 컨텍스트 |
| 4 | preempt-depth | 선점 비활성 중첩 깊이 (숫자, `.` = 0) |
| 5 | migrate-disable | 마이그레이션 비활성 깊이 |

**3번째 자리가 핵심이다.** 커널이 인터럽트 컨텍스트를 `preempt_count`의 비트로 관리하는데, 그 상태가 이 한 글자로 그대로 노출된다. 즉 **로그 한 줄만 봐도 "이 이벤트가 인터럽트 컨텍스트에서 발생했는지"를 알 수 있다.**

## 내가 캡처한 로그의 실제 판독

앞선 실습에서 나온 실제 줄들이다 (전부 재측정 없이 기존 캡처에서 발췌).

| 실제 플래그 | 이벤트 | 판독 |
|---|---|---|
| `.....` | `sys_enter`/`sys_exit` (`io_bound`) | 인터럽트 활성 + 재스케줄 요청 없음 + **프로세스 컨텍스트** + preempt_depth 0 — 가장 "평범한" 상태 |
| `d..2.` | `sched_switch` | 인터럽트 **비활성** + 프로세스 컨텍스트 + depth 2 |
| `d.h2.` `d.h3.` `d.h5.` | `sched_migrate_task` | **hardirq 컨텍스트**, 중첩 깊이 2/3/5 |
| `d.s2.` `d.s3.` `d.s4.` | `sched_migrate_task` | **softirq 컨텍스트** |
| `dns2.` | `sched_migrate_task` | 인터럽트 비활성 + **재스케줄 요청 걸림(`n`)** + softirq 컨텍스트 |

> ⚠️ 판독 주의: `dns2.`는 3번째 자리가 `s`이므로 softirq 컨텍스트다. 자리를 세지 않고 "`n`이 있으니 일반 컨텍스트"로 읽으면 틀린다. **플래그는 반드시 위치로 읽어야 한다.**

## 발견 1 — `sched_switch`가 항상 `d`(인터럽트 비활성)인 이유

캡처된 모든 `sched_switch`가 예외 없이 `d..2.`다. 우연이 아니라 **구조적 필연**이다.

컨텍스트 스위치는 런큐 락을 잡고 태스크 상태를 바꾸는 임계 구역이라, 그 사이에 인터럽트가 끼어들면 자료구조가 깨진다. 그래서 스케줄러는 인터럽트를 끄고(`d`) 선점을 비활성화한 상태(`depth 2`)에서만 스위치를 수행한다.

**역으로 활용**: 만약 로그에서 `sched_switch`가 `.`(인터럽트 활성)로 찍히면 그건 커널 버그를 의심할 신호다. 즉 이 플래그는 **정상성 검증에도 쓸 수 있다.**

## 발견 2 — 같은 이벤트가 hardirq와 softirq 양쪽에서 나온다 (top half / bottom half의 직접 증거)

가장 흥미로운 발견이다. **동일한 `sched_migrate_task` 이벤트가 어떤 줄에서는 `d.h*`(hardirq), 다른 줄에서는 `d.s*`(softirq)로 찍혔다.**

```
[000] d.h5. sched_migrate_task: comm=systemd-journal ...   <- hardirq 컨텍스트
[000] d.s4. sched_migrate_task: comm=sshd ...              <- softirq 컨텍스트
```

이건 인터럽트 처리를 **두 단계로 쪼개는 리눅스 설계(top half / bottom half)** 가 로그에 그대로 드러난 것이다:

1. **타이머 인터럽트가 발생**(hardirq, `h`) → 스케줄러 틱이 실행되며 "부하 분산이 필요하다"고 판단. 여기서 급한 결정만 내리고 즉시 빠져나온다.
2. **무거운 작업은 softirq로 미룬다**(`s`) → 실제 태스크 마이그레이션은 지연된 softirq 단계에서 수행.

즉 hardirq 컨텍스트는 "최소한만 하고 빨리 나가야 하는 구간"이고, 실제 일은 softirq로 넘긴다는 원칙이 **내 로그의 플래그 분포로 증명된 셈이다.**

`preempt_depth`가 hardirq 쪽에서 3, 5까지 올라가는 것도 같은 맥락이다 — 인터럽트가 이미 실행 중인 구간에 중첩되어 진입했다는 뜻이다.

## 발견 3 — `dns2.`: 재스케줄이 걸렸는데 즉시 못 하는 순간

`n`은 `TIF_NEED_RESCHED`가 세팅됐다는 뜻이다 — "지금 다른 태스크로 바꿔야 한다"는 요청이 이미 걸린 상태.

그런데 같은 줄의 `preempt_depth`가 2다. **선점이 비활성화되어 있어서 요청을 즉시 처리할 수 없는 상태**를 포착한 것이다. 실제 스위치는 preempt_depth가 0으로 떨어지는 시점까지 미뤄진다.

이게 실무에서 **지연(latency) 문제의 전형적인 원인**이다: 재스케줄 요청은 걸렸는데 커널이 선점 불가 구간에 있어서 응답이 늦어지는 상황. 이 한 줄이 그 순간을 잡아낸 것이다.

## 발견 4 — `irq/189-aerdrv`의 정체 (기존 관찰에 설명 붙이기)

[`log.md`](log.md) 9절에는 "PCIe AER 인터럽트가 주기적으로 프로세스를 선점"이라고만 적어뒀는데, **관찰만 있고 메커니즘 설명이 없었다.** 캡처된 줄을 다시 보면:

```
prev_comm=hot prev_prio=120 ... ==> next_comm=irq/189-aerdrv next_pid=173 next_prio=49
```

세 가지가 읽힌다.

1. **`irq/<번호>-<이름>` 형태가 프로세스로 등장한다** = 이건 하드 IRQ 핸들러가 아니라 **threaded IRQ 핸들러 커널 스레드**다. 무거운 인터럽트 처리를 프로세스 컨텍스트로 넘기는 방식(`request_threaded_irq`)으로 등록된 것. 발견 2의 "무거운 일은 미룬다"와 같은 원리의 또 다른 형태다.
2. **`next_prio=49`** — 일반 프로세스는 `prio=120`(nice 0의 커널 내부 표현 `100+20`)인데 이건 49다. RT 우선순위 영역(`0~99`)에 속한 값으로, 커널 내부 표현 `MAX_RT_PRIO-1-rt_priority`를 역산하면 **실시간 우선순위 50**에 해당한다. threaded IRQ 핸들러의 기본값이다.
3. **그래서 내 `hot` 프로세스가 밀렸다** — RT 우선순위 스레드가 깨어나면 일반 우선순위 태스크를 **즉시 선점**한다. "주기적으로 선점당했다"의 정확한 이유가 우선순위 차이였다.

또한 `sugov:0`이 `next_prio=-1`로 찍힌 것도 같은 방식으로 읽힌다 — RT 범위 밖의 음수 값은 더 높은 클래스(데드라인 스케줄링)를 뜻한다. CPU 주파수 governor가 부하 변화에 빠르게 반응해야 하므로 최상위 클래스로 동작하는 것.

**검증 예정**: 위 2·3번(RT 우선순위 50, 데드라인 클래스)은 로그에서 역산한 해석이므로, 실제 스케줄링 클래스를 `ps -eo comm,cls,rtprio`로 실측해 확정할 계획이다. (간접 추론에 머물지 않는다 — [`시행착오_기록.md`](시행착오_기록.md) 8번의 교훈)

## 이 판독으로 얻은 것

| | 이전 | 이후 |
|---|---|---|
| 인터럽트 컨텍스트 | 로그에 있었지만 못 읽음 | 플래그 3번째 자리로 즉시 식별 |
| `sched_switch`의 `d` | 의미 모름 | 락 보호를 위한 구조적 필연 + 정상성 검증 지표 |
| 마이그레이션 이벤트 | 그냥 "노이즈" | hardirq/softirq 2단계 처리의 직접 증거 |
| `irq/189-aerdrv` 선점 | "주기적으로 선점당함" | RT 우선순위 50 threaded IRQ가 nice 0을 선점 |

**핵심 교훈**: 도구가 이미 출력해준 정보를 못 읽어서 놓친 것이었다. 새 측정 없이 **같은 로그를 다시 읽는 것만으로** 네 가지 현상이 설명됐다. 캡처를 늘리는 것보다 **가진 로그를 끝까지 읽는 것**이 먼저다.
